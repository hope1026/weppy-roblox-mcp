# Visual Reference Workflow

Visual references can supply proportions, grouping, and state language that a phrase such as "game UI" leaves ambiguous. They are optional evidence, not templates or an approval gate.

## Find and interpret fitting evidence

Start with user references, the existing game, and project-owned assets. When useful and available, search for actual gameplay views with comparable camera, interaction, or screen purpose. A matching genre name alone is weak evidence. Open the images you rely on; a search title or an inaccessible image cannot establish what it looks like.

Describe what transfers: reading order, subject scale, relation to the world, surface treatment, and state separation. Also note what does not fit. A shop screenshot's density may be inappropriate for a moving player's HUD. Existing rights and asset permissions still apply; observing a game's interface does not make its imagery an asset for upload.

Search, reference count, image generation, and visual inspection are not prerequisites for every task. If a tool is unavailable, use current project evidence or choose a reasonable supported direction and disclose only material limitations. Avoid turning missing references into repeated requests for the user to supply them.

## Original comparison examples

The optional [comparison study](comparison-study.png) shows the same equipment decision in three original schematic treatments: restrained, playful, and atmospheric. It is an instructional diagram, not a Roblox screenshot or a production asset sheet. The editable [SVG source](comparison-study.svg) is included. View the PNG when image inspection is available; otherwise the explanation below carries the same principles.

- **Restrained:** paired values and a narrow accent favor quick comparison; labels carry grade and equipment state.
- **Playful:** the item illustration and broad grade-colored surface carry identity; a separate outline and equipped badge preserve simultaneous states.
- **Atmospheric:** the world remains prominent while a compact reading surface uses limited accents and text. Ornament is not required for item identity.

All three distinguish a lower cooldown as a potential benefit and expose the comparison baseline. Their particular colors, locations, shapes, English labels, and number of items are illustrative. Do not copy them as defaults or assume all games need equipment. Sparse, dense, image-free, or other compositions may fit better.

For reusable art parts and 9-slice options, see [generated assets](../../weppy-roblox-assets-guide/references/generated-assets.md). Native text, shapes, imagery, and model previews can be combined according to the requested result.

## Retain local decisions and learn from corrections

A useful correction record is brief: observed issue, chosen adjustment, and scope. For example, "combat HUD backplates obscured incoming enemies; reduce only their background paint; combat screens". Store it in existing project notes or style code when helpful, rather than requiring a new manifest.

Before applying that choice elsewhere, distinguish component, screen, and project scope. If scope is unclear, use the narrow interpretation and ask only when extending it would materially change another screen. User changes supersede earlier guesses. Do not generalize one project's correction into a universal skill policy.

When evaluating this guidance itself, compare the same request and available tools with and without the new context. Preserve raw outputs, note whether results are concepts or observed Studio views, and include dissimilar games and explicit opt-outs. A richer rationale or more code does not prove a better game. User correction effort, legibility, fit to intent, and retained choices are useful qualitative evidence; no score becomes a user's design gate.
